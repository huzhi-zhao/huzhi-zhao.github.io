# ADR-0005 内容三层结构与承载方式

- 状态：已接受
- 日期：2026-08-20
- 依赖：[ADR-0001](0001-site-positioning.md)、[ADR-0004](0004-project-card-interaction.md)

## 背景

ADR-0004 把项目卡片压成了"图 + 标题 + 一句问题句"，正文全部移走。移到哪里、由谁承载，
必须定下来，否则卡片改造无处落地。

同时存在一个长期问题：站点需要长文（技术文章、研究型 paper），
但在 Next.js 里自建 MDX 博客系统意味着要维护一整套内容管线（frontmatter 规范、
目录路由、代码高亮、目录树、搜索、图片管线），而这些和求职目标毫无关系。

## 决策

**内容分三层，各有明确的承载方式和读者：**

| 层 | 内容 | 承载 | 读者与停留时长 |
| --- | --- | --- | --- |
| L1 扫视层 | 图 + 标题 + 问题句 + 标签 | huzhi.dev 卡片 | 所有人，3 秒 |
| L2 项目层 | 项目背景、架构图、数据字典、怎么跑、结果 | ToucanShelf 知识库 public 分享页（或 Live Demo） | 有兴趣者，2–5 分钟 |
| L3 思考层 | 跨项目方法论、知识沉淀、踩坑、研究型 paper | ToucanShelf 知识库 | 技术面试官 / 架构师，5–15 分钟 |

**L2 与 L3 的边界**：L2 是**项目自身的文档**，只讲这一个项目；
L3 是**不属于任何单个项目的东西**——方法论、跨项目经验、数据质量与治理实践、研究型报告。
判据：一篇内容如果换个项目就不成立，它是 L2；如果换个项目照样成立，它是 L3。

**承载选型：全部用 ToucanShelf 知识库，站点不自建内容系统。**
huzhi.dev 只做入口——卡片链到 L2，Writing 板块链到 L3。

## 理由

- 省掉整套内容管线。站点保持为纯静态 Next.js（GitHub Pages 托管），
  内容更新不需要发版。
- **工具即作品**：ToucanShelf 是自己的开源项目，用它承载自己的内容，本身就是一层品牌叙事——
  "他不只是写了个知识库工具，他真在用它"。这是自建 MDX 拿不到的额外价值。
- L2/L3 的切分对应两类完全不同的读者需求，混在一起会让两边都不满意。

## 约束

1. **站点内不实现文章正文页**。不引入 MDX、`contentlayer`、文章路由或本地 markdown 内容目录。
   站点只持有指向知识库的 URL。
2. 知识库对应文档必须是 **public 分享状态**才能被引用。外链前需确认可匿名访问——
   一个 404 或需要登录的链接，伤害大于不放链接。
3. 外链集中在一处常量管理，便于批量检查失效。
4. L2 页面质量是 ADR-0004 卡片改造的**前提**，不是后续优化项。
   在某项目的 L2 页面就绪前，该卡片的主目标退化为 GitHub README，
   且该 README 必须按门面标准写（架构图置顶）。

## 后果

- 站点与知识库形成跨域跳转，访客会离开 huzhi.dev。接受这个代价：
  证据的可信度比停留时长重要。
- 外链存在失效风险（知识库改路径 / 取消分享），需要定期检查——
  纳入设计文档的验收清单。
- 若 ToucanShelf 的 public 分享页在移动端阅读体验不佳，会直接拖累整个 L2/L3。
  这是本决策最大的单点依赖，上线前必须实测。
