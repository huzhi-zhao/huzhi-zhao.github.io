# ADR-0019 仓库转为求职协作入口，公开边界加第三问

- 状态：提议中（2026-10-06 起草，待本人评审）
- 日期：2026-10-06
- 依赖：[ADR-0001](0001-site-positioning.md)、[ADR-0005](0005-content-tiers-and-hosting.md)、
  [ADR-0013](0013-public-repo-privacy-boundary.md)、[ADR-0014](0014-resume-scope-in-docs.md)
- 关系：**补充** ADR-0013（前两问不变，加第三问），**回答** ADR-0014 的复审条件

## 背景

站点已经稳定，此后只剩维护。仓库的用途却在变：它挂上了 ToucanShelf 的
Career 和 SideProjects 两个库（`kb/`），会话的重心从"改站点"转到了求职本身。
长期的工作线有六条：

1. 模拟面试——正在规划，目标是养成习惯；
2. 本地活动巡检——正在做；
3. 专业认证；
4. 简历修改（已有链路，见 ADR-0013"简历的生成链路"）；
5. 做面向求职的项目；
6. 将来实际投递。

两个问题随之而来。

**一是仓库要不要跟着改。** `CLAUDE.md` 还写着"huzhi.dev 个人站点"，
新会话读到的前提只覆盖站点和简历，其余四条工作线没有路由：
不知道该读哪里、写哪里，也不知道哪些东西不能落进仓库。

**二是公开边界够不够。** ADR-0013 用两问划线：是不是简历事实，是不是住址或手机号。
那时仓库里只有站点和简历方法论，两问够用。现在多出来的是**求职过程信息**——
投给了谁、面试复盘、差距分析、简历哪句经不起追问、认证进度——
它们既不是简历事实，也不是住址电话，两问都放行，却正是最不该公开的一类。

而且读者是同一批人。站点导航栏和 Contact 都链到 GitHub 主页，本仓库离面试官只有一次点击。
ADR-0013 否掉"渐进泄漏"时，假设的是陌生人拼画像；这里的威胁不是陌生人，
是**正在评估你的那个人**读到你给自己写的弱点清单。

## 决策

### 1. 仓库定位：求职工作的 Claude Code 协作入口

仓库同时是两样东西：站点源码，以及六条求职工作线的协作入口。
后者的意思是**规则在这里，内容不在这里**：

- 仓库放：怎么协作、写哪边（`CLAUDE.md`、`docs/collaboration/`）；
  可公开的事实与方法论（`lib/content/`、`docs/resume/`）；简历与站点的决策（`docs/adr/`）。
- ToucanShelf 放：每条工作线的过程、素材、记录与待办。

站点进入维护期。维护指的是：事实同步（ADR-0007 约束 4）、到期复审（如 ADR-0008）、
新项目上架（ADR-0005）。不做新板块、不做改版，除非先有 ADR。

### 2. 六条工作线各自落在哪里

| 工作线 | 过程与记录 | 仓库侧有什么 |
| --- | --- | --- |
| 模拟面试 | `Career/Interview/` | 只放通用的协作方式（若有），不放题库、答案、复盘 |
| 活动巡检 | `Career/Campaigns/` 的巡检战役 | 无 |
| 专业认证 | `Career/Campaigns/`（选型与进度） | 拿到之后怎么写，按资历归属的 ADR（ADR-0017，提议中） |
| 简历修改 | `Career/Vault/`（裁剪稿）、`Career/Experience/`（素材） | `docs/resume/` 方法论、`lib/content/` 事实，链路不变 |
| 求职项目 | 代码在各自的仓库；文档在 `SideProjects/{project}/`；为什么做、对准什么岗位在 `Career/` | 做成之后按 ADR-0003 / 0005 上架 Projects |
| 投递 | `Career/Campaigns/`、`Career/Contacts/Employers/` | 无 |

Career 内部怎么分子目录，以它自己的 `README` 为准。这张表只定"在仓库还是在知识库"。

### 3. 公开边界加第三问

ADR-0013 的两问之后，再问一句：

> **这段内容被面试官读到，会不会削弱我？**

会的，不进仓库。这一类统称**求职过程信息**，至少包括：

- 投递对象、投递状态、面试安排，以及与具体雇主的往来；
- 面试题、答案、复盘与反馈；
- 自评的弱点、差距分析、能力短板；
- 简历条目的证据缺口——哪个数字没有度量、哪段素材拿不出来、被追问时怎么答；
- 认证、考试的进度与成绩；
- 目标岗位的排序与备选方向；
- 求职时间线的个人约束、身份状态、薪资期望；
- 活动与人脉里遇到的具体的人（ADR-0013 约束 1 本已覆盖）。

**指针也算。** 仓库里引用 Career 文档时，如果路径或标题本身就带着上面的信息
（雇主名、战役名、岗位名），改用泛指，例如"见 `Career/Campaigns/` 对应战役"。
ADR-0013 约束 4"只引位置不引内容"在这里收紧为：**位置本身也不能泄漏内容**。

同样适用于 commit message、分支名和 PR 描述——它们与文件一起公开，删文件删不掉它们。

### 4. `TODO.md` 只管仓库侧

`TODO.md` 收窄为**仓库侧待办**：站点、文档、方法论、跨系统的事实同步。
求职工作线的待办留在 Career 各战役的"待办"段，素材缺口留在 `Career/Experience/`。

### 5. 已经进了仓库的

按第三问清理当前版本。git 历史里的旧内容要不要重写历史来清除，
属于不可逆操作，由本人决定，结果回写到本节。

## 理由

- **读者重合是事实，不是假设。** ADR-0013 不纳入渐进泄漏，是因为站点不做主动分发、
  陌生人没有动机拼画像。第三问不依赖这个前提：它针对的读者正是被递了简历、
  点进站点、再点进 GitHub 的那个人。只要站点还链着 GitHub，这条就成立。
- **不对称。** 求职过程信息公开出去，对本人没有任何收益；落到面试官手里，
  每一条都可能变成追问或扣分点。没有需要权衡的另一头。
- **判断成本低。** ADR-0013 否掉渐进泄漏的主要理由是"每条事实都要判断能不能写"。
  第三问按**类别**判断，不按单条事实判断；而且这些内容在 Career 里本来就有归宿，
  不进仓库不会让任何工作被迫跨系统。
- **规则在仓库、内容在知识库，云端会话也能走通。** `kb/` 已是会话开场的硬前提，
  会话需要的上下文都能从 `kb/` 读到，不需要仓库替它保存副本。

## 约束

1. 求职过程信息（决策 §3 的清单）不进仓库：文件、指针、commit message、分支名、PR 描述都算。
2. 引用 Career 文档时，路径或标题带雇主名、岗位名、战役名的，用泛指代替。
3. 证据引用只写位置，不复述理由中的过程信息。ADR 需要依据时写"依据见 `Career/decisions/`"，
   不在仓库展开排序、备选或个人约束。
4. `TODO.md` 只记仓库侧待办，求职工作线的待办不进来。
5. 站点维护期内不新增板块、不改版，除非先有 ADR。
6. 前两问（ADR-0013）不变，渐进泄漏仍不作为约束依据。第三问只挡上述类别，
   不扩展成"每条事实都要判断"。

## 后果

- 正面：新会话一进来就知道六条线各去哪里；公开仓库不再承载对本人不利的信息；
  `TODO.md` 回到一页能看完的规模。
- 负面：有些 ADR 的"背景 / 理由"只能写成指针，单看仓库读不出完整依据，
  要配合 `kb/` 读。这是有意接受的——依据本来就在 Career。
- 负面：git 历史里的旧内容在本人决定之前依然可查。

## 与既有 ADR 的关系

- **ADR-0013**：补充，不推翻。两问与"渐进泄漏不作依据"都保留；第三问另起一类。
  其复审条件"把站点网址写进批量投递的简历"触发后，仓库侧已由本 ADR 覆盖，
  届时只需复审站点侧。
- **ADR-0014**：其复审条件是"进入密集投递期、需要版本管理时，是否开独立仓库"。
  回答是**仍然不开**：针对性版本放在 `Career/Vault/`，从不在仓库，
  版本管理不是仓库的问题。
- **ADR-0001 / 0008**：不受影响。站点仍然不是简历，求职意向的时间边界不变。

## 复审条件

- 仓库改为 private，或站点不再链接 GitHub——第三问的前提（读者重合）减弱，可以放宽；
- 求职告一段落（拿到 offer）——六条工作线大部分结束，仓库定位回到站点本身；
- 出现确需在仓库里留存的求职产物（例如开源的面试练习工具）——
  判断它是方法论还是过程信息，再定是否需要拆出去。
